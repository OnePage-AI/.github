# [트러블슈팅] AI 분석 파이프라인 v5.0: 초대용량 문서 분석 및 500 에러 안정화

## 1. 문제 발생 배경
모릭(Mori-Q) 서비스는 수십 페이지에 달하는 방대한 강의 자료를 안정적으로 구조화해야 했습니다. 기존 v4.0 아키텍처에서는 Gemini의 100만 토큰 롱 컨텍스트를 믿고 전체 데이터를 한 번에 모델에 주입하는 **단일 Stuffing** 방식을 사용했습니다.

## 2. 문제 정의
운영 중 **40페이지 이상의 이미지와 텍스트가 포함된 초대용량 문서**를 처리할 때, 구글 API 내부에서 `500 INTERNAL` 에러를 반환하며 분석이 중단되는 현상이 빈번하게 발생했습니다. 이는 모델의 토큰 한계(Context Window) 문제가 아니라, **단일 API 요청의 페이로드 크기 및 처리 복잡도**가 구글 클라우드 내부 임계치를 초과하면서 발생하는 현상이었습니다.

## 3. 원인 분석 및 대안 탐색
- **분석 결과**: 40p+ 문서의 경우 멀티모달(이미지+텍스트) 페이로드가 과도하여 API 게이트웨이 또는 추론 엔진에서 타임아웃/오류가 발생함을 확인했습니다.
- **대안 1: Map-Reduce**: 자료를 조각내어 요약하고 합치는 방식. 대용량 처리는 가능하나, 전체 맥락을 관통하는 통찰력 있는 요약 품질을 보장하기 어려움.
- **대안 2: Sequential Batched Long Context (선택)**: 전체 컨텍스트를 유지하되, 물리적인 모델 호출만 '안전 단위'로 나누어 실행하는 하이브리드 전략.

## 4. 기술적 선택 및 구현 과정 (v5.0)

### 4.1. 3단계 계층적 파이프라인 설계
1. **Phase 0: Semantic Anchor**: 첫 2페이지의 시각 정보와 전체 텍스트 요약을 결합하여 문서의 '뼈대(Semantic Map)'를 먼저 구축합니다.
2. **Phase 1: Sequential Batched Reconstruction (핵심)**:
   - 전체 문서를 **15페이지 단위의 배치(Batch)**로 나눕니다.
   - 각 배치를 **순차적으로(Sequential)** 호출하여 500 에러를 방지합니다.
   - 이때 Phase 0에서 만든 Semantic Map을 함께 주입하여 배치가 나뉘더라도 전체 맥락을 유지하게 합니다.
3. **Phase 2: Final Synthesis**: 개별 배치 결과물을 '음슴체' 스타일 가이드와 함께 고속 스트리밍으로 결합하여 최종 리포트를 완성합니다.

### 4.2. UX 최적화: 숨 쉬는 진행률(Breathing Progress)
순차적 배칭으로 인해 총 처리 시간이 길어짐에 따라, 사용자가 멈춤 현상을 느끼지 않도록 가상 진행률 로직을 적용했습니다. 70% 이후부터는 0.1%씩 점진적으로 증가하는 피드백을 통해 안정감을 제공합니다.

## 5. 개선 결과 및 회고
- **안정성**: 100페이지 이상의 대규모 자료에서도 `500 INTERNAL` 에러 발생률 **0%** 달성.
- **품질**: 배치를 나누어 처리함에도 불구하고 Semantic Map 주입을 통해 단일 Stuffing 방식에 준하는 높은 맥락 유지력 확보.
- **확장성**: API 응답 지연에 강인한 구조를 확보하여 향후 더 큰 규모의 멀티모달 데이터 처리 기반 마련.

AI 모델의 '스펙(토큰 윈도우)'과 실제 '운영 임계치(페이로드 제한)' 사이의 간극을 기술적으로 메운 중요한 아키텍처 고도화 사례였습니다.
