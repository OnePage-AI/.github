# [트러블슈팅] AI 서버의 물리적 보호: asyncio.Semaphore를 활용한 동시성 제어

## 1. 문제 상황
GCP Cloud Run 환경에서 운영 중인 AI 워커가 대규모 사용자의 동시 요청을 받을 때, 메모리 부족으로 인한 **컨테이너 크래시(Crash)** 혹은 Gemini API의 **429 Rate Limit(할당량 초과)** 오류가 빈번하게 발생했습니다. 특히 대용량 문서는 단일 요청만으로도 수십 개의 이미지 페이로드를 포함하여 서버 자원을 극심하게 소모했습니다.

## 2. 병목 분석 및 가설
*   **리소스 고갈**: 비동기 워커가 큐에서 작업을 제한 없이 가져와 실행할 경우, CPU와 메모리 사용량이 급증하여 운영 인프라의 안정성을 저해합니다.
*   **할당량 위반**: 모델 호출 동시성이 지나치게 높으면 API 제공업체의 속도 제한 정책에 걸려 모든 사용자의 분석이 실패하게 됩니다.

## 3. 해결 시도 및 구조 재설계: 물리적 동시성 제한
애플리케이션 레벨에서 실제 AI 연산을 수행하는 스레드 수를 엄격히 제어하기 위해 `asyncio.Semaphore`를 도입했습니다.

### 3.1. 세마포어 기반 큐 대기 구조
전체 시스템의 `max_jobs` 설정과 별개로, 실제 모델을 호출하는 핵심 로직 진입점에 **세마포어(값: 2)**를 배치했습니다.
```python
# worker/tasks.py 예시 로직
semaphore = asyncio.Semaphore(2)

async def process_ai_task(payload):
    async with semaphore:
        # 이 블록 내부에는 최대 2개의 비동기 태스크만 진입 가능
        result = await call_gemini_api(payload)
        return result
```

## 4. 최종 안정화 및 결과
*   **서버 안정성**: 동시 요청이 몰려도 실제 무거운 연산은 2개씩 순차 처리되므로, 메모리 피크(Peak) 현상이 사라지고 컨테이너 강제 종료가 발생하지 않습니다.
*   **에러율 감소**: 429 및 503 에러 발생 빈도가 비약적으로 감소하여, 재시도 로직의 부담이 줄어들고 전체적인 분석 성공률이 향상되었습니다.

인프라의 자동 스케일링(Auto-scaling)에만 의존하기보다, **애플리케이션 스스로 리소스 사용량을 통제하는 가드레일**을 설계하는 것이 고부하 AI 서비스 운영의 핵심임을 확인했습니다.
