# [트러블슈팅] Firestore에서 PostgreSQL(Cloud SQL)로의 데이터베이스 전환

## 1. 문제 발생 배경
OnePage 서비스는 초기 개발 단계에서 스키마리스(Schema-less)의 유연성과 빠른 프로토타이핑을 위해 **Google Firestore**를 주 데이터베이스로 사용했습니다. 그러나 서비스가 고도화됨에 따라 다음과 같은 한계에 직면했습니다.

- **복잡한 쿼리의 한계**: 강의 이력, 요약 결과, 사용자 크레딧 등을 조합한 다중 조건 검색 및 통계 쿼리 작성이 어려움.
- **데이터 정합성 유지 비용**: 비정상적인 종료나 동시성 경합 상황에서 원자성(Atomicity)을 보장하기 위한 트랜잭션 로직이 복잡해짐.
- **관계형 데이터의 부재**: 사용자와 강의자료 간의 1:N 관계 등을 관리하기 위해 중복 데이터를 허용하거나 클라이언트 단에서 조인(Join)해야 하는 비효율 발생.

## 2. 문제 정의
시스템 아키텍처가 단순 '문서 저장'을 넘어 '지식 구조화 관리'로 확장됨에 따라, 관계형 데이터베이스(RDBMS) 도입을 통한 데이터 무결성 확보와 쿼리 성능 최적화가 필수 과제로 식별되었습니다.

## 3. 원인 분석 및 대안 탐색
- **Firestore 유지**: 유연하지만 복잡한 관계 표현 시 성능 저하 및 관리 비용 상승.
- **PostgreSQL (선택)**: 강력한 관계형 모델링, JSONB 지원을 통한 반정규화 데이터 수용, SQLAlchemy(Python) 및 JPA(Java)와의 우수한 호환성.

## 4. 기술적 선택 및 구현 과정

### 4.1. 하이브리드 저장 전략
완전한 이전 대신, 각 DB의 장점을 살린 하이브리드 구조를 설계했습니다.
- **PostgreSQL (Cloud SQL)**: 사용자 정보, 강의 메타데이터, 요약 결과(JSON), 작업(Task) 상태 등 정형 데이터 관리.
- **GCS (Cloud Storage)**: 대용량 PDF 원본 및 페이지별 이미지 데이터 저장.
- **Redis (Upstash)**: 비동기 작업 큐 및 캐시 저장소.

### 4.2. 백엔드 연동 (onepage-be & onepage-ai)
- **onepage-be**: Spring Boot에서 **Spring Data JPA**를 사용하여 도메인 로직과 DB 간의 정합성 보장.
- **onepage-ai**: **SQLAlchemy (asyncio)**를 도입하여 워커 프로세스에서 비동기적으로 작업 상태를 업데이트하고 결과를 저장하는 파이프라인 구축.

### 4.3. 데이터 마이그레이션 및 동기화
- 기존 Firestore에 분산되어 있던 데이터를 PostgreSQL 스키마에 맞춰 재설계.
- `AsyncSessionLocal`을 통한 세션 관리로 워커 내 DB I/O 안정성 확보.

## 5. 개선 결과 및 회고
- **쿼리 성능 향상**: 복잡한 강의 이력 조회 및 사용자 상태 확인 속도가 비약적으로 개선됨.
- **정합성 확보**: 데이터베이스 제약 조건(Foreign Key, Unique 등)을 통해 어플리케이션 레벨의 방어 로직 없이도 데이터 무결성 유지 가능.
- **확장성**: 향후 결제 시스템, 관리자 대시보드 등 복잡한 비즈니스 로직 추가를 위한 견고한 데이터 기반 마련.

이번 전환을 통해 '빠른 개발'보다 '견고한 시스템'이 서비스 장기 운영에 얼마나 중요한지 다시 한번 확인했습니다.
