### 동시 처리량의 한계

---

Grafana와 Prometheus, 그리고 Locust를 활용하여 가상의 사용자 100명에 대한 부하 테스트를
진행한 결과, 실시간 처리 중인 요청 수 그래프가 시스템 임계치인 80을
지속적으로 초과하는 현상이 관측되었습니다.

![image.png](attachment:6b2cf941-7608-40ba-b42f-0374d8bcaa77:image.png)

현재 GCP Cloud Run 설정상, 단일 인스턴스가 동시에 처리할 수 있는 최대 요청 수는 80개로
제한되어 있습니다.

![image.png](attachment:172a44c6-c099-40c7-8473-77c61a00e151:image.png)

따라서 이 수치를 넘어서는 요청들은 대기열(Queue)에 쌓이거나, 처리 지연이 길어질 경우 503 Service Unavailable 에러를 유발하여 사용자 경험을 심각하게 저해할 수 있습니다.

### 병목 구간 진단

---

![image.png](attachment:b09edc55-ac65-4abc-9934-79b3c73113fd:image.png)

현재 인프라 구성은 다음과 같습니다.

- 최대 인스턴스 수 : 3개
- 인스턴스당 처리량 : 80명
- 총 처리 용량 : 3개 × 80명 = 240명

서비스의 핵심 기능인 'AI 강의 복습'이 평균 15초 이상의 처리 시간을 요한다는 점이 문제입니다.
만약 300명의 사용자가 동시에 접속한다면, 240명은 정상적으로 서비스를 이용할 수
있지만, 나머지 60명은 하염없이 대기해야 하는 병목 현상이 발생하게 됩니다.

이를 해결하기 위해서는 시스템의 '용량'을 늘리거나, '처리 속도'를 높여야 합니다.

### 병목 해소를 위한 방법들

---

**1. 수직/수평 확장**
가장 직관적인 방법은 인스턴스의 개수를 늘리는 것
300명의 동시 접속자를 수용하기 위해서는 최소 4개 이상의 인스턴스가 필요

- 장점: 코드 수정 없이 설정 변경만으로 즉시 해결 가능
- 비용: Cloud Run은 사용량 기반 과금이므로, 트래픽이 몰리는 시간에만 비용이 발생하여
  합리적

**2. 처리 시간 단축**
개별 요청 처리 시간을 15초에서 1초로 단축할 수 있다면 동일한 자원으로 15배 많은 트래픽을
처리 가능

하지만 현재 병목의 주원인은 외부 Google Gemini API의 응답 대기
시간이므로, 내부 로직 최적화만으로는 유의미한 속도 개선이 어려움

3. 비동기 아키텍처 도입
   사용자가 결과가 나올 때까지 15초간 연결을 유지하며 기다리는 구조를 해결하는 근본적인 해결책

1. 요청 접수: 사용자의 요청을 받자마자 응답을 즉시(0.1초 내) 반환하고
   연결을 끊음 -> 동시 접속자 부하 99% 감소
2. 비동기 처리: 실제 AI 요약 작업은 백그라운드 큐(Cloud Tasks, Celery 등)에서 순차적으로
   처리
3. 사용자는 폴링이나 알림을 통해 완료된 결과 확인 가능

### 문제 재정의

---

단순히 인스턴스를 늘리는 것(대안 1)은 임시방편일 뿐입니다.
사용자가 늘어날 때마다 인스턴스 비용은 선형적으로 증가하며, 결국 어느 시점에는 비용 효율이 급격히 떨어지게 됩니다. 또한, 긴 대기 시간(15초)을 유지하는 동기식 구조는 네트워크 불안정으로 인한 타임아웃 오류에 취약합니다.

따라서, 지금 당장의 개발 리소스가 조금 들더라도 미래의 기술 부채와 운영 리스크를 원천
차단하기 위해 비동기 큐 시스템을 선제적으로 도입하는 것이 가장 합리적인 선택입니다.

**비동기 구조 도입 시 기대 효과**

- 동시 접속자 무제한 수용: 서버가 사용자의 연결을 0.1초 만에 끊어주므로, 적은 수의
  인스턴스(3개)로도 수천, 수만 명의 요청을 접수받을 수 있음
- 비용 절감: 15초 동안 아무것도 안하며 기다리는 유휴 자원이 사라지므로, 동일한 비용으로 훨씬 더 많은 작업을 처리할 수 있음
- 안정성 확보: 외부 API(Gemini)가 느려지거나 장애가 발생해도, 사용자 요청은 안전하게 큐에
  저장되어 유실되지 않음

### 실행 계획 및 실제 구현 (v5.0)

---

기존의 동기식 수직/수평 확장 대신, 시스템의 안정성과 제어권을 확보하기 위해 **Redis + ARQ** 기반의 비동기 아키텍처를 최종적으로 구축했습니다.

1.  **비동기 큐 (Redis + ARQ)**: 사용자 요청을 즉시 처리하지 않고 Redis 큐(arq)에 적재합니다.
2.  **Worker 분리 및 최적화**: 
    - `max_jobs`를 **2**로 하향 조정하여 단일 인스턴스 내 AI 모델 호출 부하를 제어하고 503 에러를 원천 차단했습니다.
    - `job_timeout`을 **3600초(60분)**로 대폭 상향하여 대용량 강의 자료 분석 중단 현상을 해결했습니다.
3.  **상태 저장소 (PostgreSQL/Firestore)**: 작업 상태와 결과를 영속적으로 저장하여 안정적인 폴링 환경을 제공합니다.
4.  **프론트엔드 실시간 모니터링**: `TaskMonitor` 컴포넌트를 통해 사용자가 70% 이후에도 '숨 쉬는 진행률'을 보며 신뢰를 유지하도록 UX를 최적화했습니다.

**최종 개선 결과**
- 300명 이상의 동시 접속자가 발생해도 서버는 0.1초 내에 요청을 수락하고 큐에 안전하게 보관합니다.
- Gemini API의 응답 속도와 관계없이 사용자는 타임아웃(504) 없는 안정적인 서비스를 경험하게 되었습니다.
