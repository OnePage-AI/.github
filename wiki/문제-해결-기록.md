# 시스템 개선 및 문제 해결 기록

이 페이지는 원페이지(OnePage) 운영 환경에서 발생한 병목과 리스크를 점진적으로 이해하고 개선해 나간 엔지니어링 기록입니다. 단순한 기능 구현을 넘어, 시스템 내부 동작과 리소스 관리 관점에서 아키텍처를 진화시킨 과정을 담고 있습니다.

## 1. 동기식 AI 파이프라인의 한계 돌파부터 RDBMS 동시성 제어까지

### 1.1. 문제 상황: 리소스 점유 시간이 만든 아키텍처의 한계
초기 아키텍처는 클라이언트의 요청이 들어오면 백엔드 API 서버가 직접 Gemini API를 호출하고 결과를 반환하는 **동기(Synchronous) 방식**으로 구현되어 있었습니다. AI 추론 작업은 문서 분량에 따라 최소 15초에서 60초 이상 소요되었고, 사용자가 증가함에 따라 심각한 운영 문제가 발생했습니다.

*   **Thread Blocking 및 Connection Pool 고갈:** API 서버가 AI 응답을 기다리는 동안 HTTP 커넥션과 스레드를 점유한 채 대기(Blocking)합니다.
*   **인스턴스 동시성 임계치 초과:** 단일 인스턴스 최대 동시 처리량(80개)에 도달하면서 신규 요청이 대기열에 쌓이거나 **504 Gateway Timeout** 에러가 쏟아졌습니다.
*   **데이터 무결성 훼손:** 사용자가 기다리다 브라우저를 새로고침할 경우, 서버는 연산을 완료했음에도 클라이언트가 결과를 받지 못해 '크레딧만 차감되고 결과는 유실되는' 현상이 발생했습니다.

### 1.2. 최초 문제 발견 및 해결 시도: 비동기 큐 도입
k6를 활용한 100명 동시 접속 부하 테스트 결과, 80번째 요청 이후 20%의 요청이 타임아웃으로 실패했습니다. 리소스 점유 시간을 최소화하기 위해 API 서버와 AI 워커(Worker)를 분리하는 **비동기 큐(Asynchronous Queue) 아키텍처**를 설계했습니다.

*   **Redis + ARQ (채택):** 애플리케이션 레벨에서 큐를 제어하여 타임아웃과 재시도 정책을 세밀하게 조정할 수 있어, 로컬과 운영 환경의 일관성을 확보했습니다.
*   **개선된 흐름:** API 서버는 요청을 받자마자 Redis 큐에 적재하고 클라이언트에게 `task_id`를 0.1초 이내에 반환하여 커넥션을 끊습니다. 백그라운드 워커가 작업을 처리하고 클라이언트는 폴링으로 결과를 조회합니다.

### 1.3. 새로운 문제 발견: 데이터베이스 경합과 Deadlock
비동기 전환으로 인프라 타임아웃은 해결되었으나, 워커들이 백그라운드에서 병렬로 빠르게 작업을 쏟아내면서 새로운 병목이 드러났습니다. 다수의 워커가 동시에 AI 분석 결과를 저장하고 사용자의 크레딧을 차감하는 과정에서 `Lock Wait Timeout` 및 초과 인출(크레딧 마이너스) 오류가 폭증했습니다. 

*   CountDownLatch를 사용한 멀티스레드 동시성 테스트를 통해 Race Condition을 재현한 결과, 트랜잭션 충돌과 Deadlock이 확정적으로 발생했습니다.

### 1.4. DB 내부 메커니즘 분석: 실행 계획과 락의 충돌
*   **EXPLAIN 분석과 락 범위 확산:** 태스크 상태 업데이트 쿼리의 실행 계획을 분석한 결과, `task_id` 필드에 인덱스가 누락되어 **Full Table Scan**이 발생했습니다. RDBMS는 스캔하는 모든 레코드에 락을 걸기 때문에 불필요한 범위까지 락이 확산되어 다른 워커들의 트랜잭션을 블로킹하고 있었습니다.
*   **Deadlock 로그 분석:** 워커 A와 B가 동일 사용자 크레딧을 읽기 위해 S-Lock(Shared Lock)을 획득한 후, 차감을 위해 X-Lock(Exclusive Lock)으로 승격(Lock Escalation)하려 할 때 서로의 S-Lock을 대기하는 교착 상태(Deadlock)가 확인되었습니다.

### 1.5. 최종 구조 개선: 락 범위 국소화 및 원자적 연산
1.  **인덱스 설계와 Record Lock 유도:** `task_id`에 Unique Index를 추가하여 Full Table Scan을 방지하고 락 범위를 단일 행(Record Lock)으로 국소화했습니다.
2.  **트랜잭션 범위 축소와 Atomic Update:** 어플리케이션 레벨의 Read-Modify-Write 패턴을 버리고, 데이터베이스 레벨의 **원자적 쿼리(Atomic Query)**를 도입했습니다.
    ```sql
    UPDATE users SET available_credits = available_credits - 1 
    WHERE uid = :uid AND available_credits > 0;
    ```
    이 쿼리는 S-Lock 획득 없이 즉시 X-Lock을 쥐고 연산을 수행하므로 Deadlock과 초과 인출을 원천 차단합니다.
3.  **트랜잭션과 외부 I/O 분리:** 수십 초가 걸리는 Gemini API 호출을 DB 트랜잭션 외부로 분리하여 Connection 장기 점유를 해결했습니다.

**[개선 결과]** 멀티스레드 테스트에서 크레딧 초과 인출이 완벽히 차단되었으며, MySQL `performance_schema` 관찰 결과 UPDATE 구간의 Lock Wait 누적 현상이 완전히 사라졌습니다. 분산 락(Redisson) 대신 원자적 쿼리와 인덱스 최적화만으로 동시성을 제어하여 운영 복잡도 없이 문제를 해결했습니다.

## 2. 로그인 직후 세션 만료 문제: Race Condition 분석과 Stateless 인증 도입

### 2.1. 문제 상황 및 최초 발견
"로그인 직후 바로 페이지를 새로고침하면 로그아웃되는 현상"이 간헐적으로 발생했습니다. 반면 로그인 후 API를 한 번이라도 호출한 뒤 새로고침하면 정상 유지되었습니다.

### 2.2. 원인 분석 및 가설 검증
프론트엔드의 토큰 갱신 로직에는 문제가 없었으므로 백엔드와 DB 사이의 타이밍을 분석했습니다.
1.  백엔드가 토큰을 생성하고 비동기로 DB에 저장 명령을 내리면서 프론트엔드로 응답을 반환.
2.  프론트엔드가 응답 수신 직후 새로고침하여 토큰 재발급(Reissue) 요청.
3.  백엔드가 DB에서 Refresh Token을 조회하지만, DB I/O 지연으로 아직 저장이 완료되지 않아 `401 Unauthorized` 반환 (Race Condition).

### 2.3. 구조 재설계 및 DB 내부 분석
기존 방식은 Stateful 인증 구조로, DB에서 토큰을 매번 조회하는 로직이 원인이었습니다. Race Condition을 근본적으로 해결하기 위해 DB 조회 의존성을 제거하고 JWT의 자체 서명(Signature)만으로 검증하는 **Stateless 방식**으로 변경했습니다.

*   **Architectural Decision:** Stateless 방식으로 전환하면 서버에서 특정 토큰을 강제 무효화(Revoke)할 수 없는 보안 단점이 생깁니다. 이를 상쇄하기 위해 Refresh Token의 유효 기간을 기존 14일에서 1일로 대폭 단축하여 리스크를 관리했습니다.

**[개선 결과]** DB I/O 속도와 관계없이 토큰 검증이 가능해져 Race Condition이 원천 차단되었으며, 재발급 시 발생하던 불필요한 DB 조회 쿼리가 제거되어 인증 응답 속도도 개선되었습니다.

## 3. 초대용량 문서 분석의 한계와 AI 파이프라인 최적화

### 3.1. 문제 상황
40페이지 이상의 복잡한 멀티모달(텍스트+이미지) 문서를 한 번에 AI 모델에 주입할 때 구글 클라우드 내부에서 `500 INTERNAL` 에러를 반환하며 분석이 중단되는 현상이 지속적으로 발생했습니다.

### 3.2. 병목 분석 및 가설
이는 모델의 Context Window 한계(100만 토큰) 문제가 아니라, 단일 API 요청에 담긴 페이로드 크기 및 연산 복잡도가 API 게이트웨이의 운영 임계치를 초과하면서 발생하는 문제로 판단했습니다.

*   **대안 비교:** 데이터를 단순히 조각내어 요약하는 Map-Reduce 방식은 처리 용량은 늘릴 수 있으나, 전체 강의의 흐름과 맥락이 파편화되어 요약 품질이 급격히 떨어지는 한계가 있었습니다.

### 3.3. 구조 재설계: Sequential Batched Long Context
문서의 전체 문맥을 유지하면서 500 에러를 피하기 위해 **Sequential Batched Long Context** 하이브리드 전략을 설계했습니다.

1.  **Phase 0 (Semantic Anchor):** 문서 첫 2페이지의 시각 정보와 전체 텍스트 요약을 결합해 문서의 뼈대(Semantic Map)를 우선 추출.
2.  **Phase 1 (Sequential Batch):** 전체 문서를 15페이지 단위의 안전 배치(Batch)로 나누고 순차적으로(Sequential) 모델에 주입. 이때 Phase 0의 뼈대를 함께 주입해 파편화를 방지.
3.  **Phase 2 (Final Synthesis):** 개별 배치 결과를 고속 스트리밍으로 결합.

### 3.4. 운영 리스크 대응: 404 에러와 Graceful Degradation
비용 절감을 위해 일부 파이프라인에 경량 모델인 `gemini-2.5-flash-lite`를 도입했으나, 아시아 리전(asia-northeast1)에서 간헐적으로 `404 Publisher Model was not found` 에러가 발생했습니다.

*   **판단:** 인프라 배포의 불확실성을 감수하기보다 시스템의 가용성이 우선이라 판단했습니다. 비용 효율성보다 운영 안정성을 지키기 위해 모델을 `gemini-2.5-flash`로 즉각 일원화(Graceful Degradation)했습니다.

**[개선 결과]** 100페이지가 넘는 대용량 자료에서도 500 에러율 0%를 달성했으며, 배치를 나누어 처리함에도 불구하고 단일 주입(Stuffing) 방식에 준하는 높은 맥락 유지력을 확보했습니다.

## 4. "Design is Modern, Data is Classic": 마크다운 엔진의 회복 탄력성 확보

### 4.1. 문제 발견: 데이터 호환성과 렌더링 깨짐
초기에는 정교한 UI 표현을 위해 분석 결과를 JSON 객체로 받았으나, 사용자가 결과를 복사하여 외부 도구(Notion 등)로 가져갈 때 데이터 무결성이 훼손되는 문제가 있었습니다. 이를 위해 데이터 규격을 표준 마크다운으로 회귀시켰으나, AI가 생성하는 불완전한 문법(공백 누락, Sticky Bullets 등)으로 인해 렌더링이 자주 깨지는 현상이 발생했습니다.

### 4.2. 내부 메커니즘 분석 및 해결: Resilience Preprocessor
AI의 사소한 포맷 오류를 수용하고 보정하기 위해 프론트엔드에 **회복 탄력적 전처리기(Resilience Preprocessor)**를 도입했습니다.

1.  **문법 정규화**: 정규표현식을 통해 불렛 기호 뒤 공백 강제 삽입, 문장 끝 불렛 강제 개행 등을 수행하여 AST 파싱 안정성 확보.
2.  **지능형 페이지 참조**: AI가 남기는 다양한 형태의 페이지 참조(`[Page n]`, `Slide n` 등)를 감지하여 클릭 시 PDF 해당 위치로 이동하는 **인터랙티브 칩**으로 동적 변환.

**[개선 결과]** AI의 불완전한 출력을 프론트엔드에서 실시간 보정함으로써, 데이터의 순수성(Markdown)과 세련된 UI/UX(Interactive Chips)를 동시에 실현했습니다.

## 5. AI 서버의 물리적 보호: asyncio.Semaphore를 활용한 동시성 제어

### 5.1. 문제 상황: 리소스 고갈과 컨테이너 크래시
대규모 동시 요청 유입 시, 비동기 워커가 작업을 제한 없이 실행하면서 메모리 사용량이 급증하여 컨테이너가 강제 종료(Crash)되거나 API 할당량 초과(429) 에러가 발생했습니다.

### 5.2. 해결 시도 및 구조 재설계: 물리적 동시성 제한
애플리케이션 레벨에서 실제 AI 연산을 수행하는 스레드 수를 엄격히 통제하기 위해 `asyncio.Semaphore`를 도입했습니다.

*   **세마포어 가드레일**: 전체 작업 큐(Queue) 설정과 별개로, 실제 모델 호출 진입점에 세마포어(값: 2)를 배치하여 무거운 연산은 항상 순차적으로 처리되도록 보장했습니다.

**[개선 결과]** 인프라의 자동 스케일링에만 의존하지 않고 애플리케이션 스스로 리소스 피크를 관리하게 되어, 고부하 상황에서도 서버 생존율과 분석 성공률이 비약적으로 향상되었습니다.

## 6. 끊김 없는 온보딩: 중간 로그인 시 상태 보존(State Preservation)

### 6.1. 문제 발견: 로그인 리다이렉트 시 작업 초기화
사용자가 비회원 상태에서 파일 업로드와 분석 범위 설정을 마친 뒤 로그인을 진행하면, 페이지 새로고침으로 인해 **모든 작업 상태가 초기화**되어 처음부터 다시 시작해야 하는 이탈 요인이 발견되었습니다.

### 2. 해결 시도 및 재설계: Modal-First 인증 및 State Forwarding
1.  **Auth-Forwarding**: 작업 중인 상태값을 URL 파라미터나 세션 브리지에 인코딩하여 로그인 후에도 해당 상태를 복원할 수 있도록 설계.
2.  **Modal-First 흐름**: 페이지 이동이 아닌 모달 기반 로그인을 통해 React 상태를 메모리에 보존한 상태로 인증 정보만 동적으로 업데이트.

**[개선 결과]** 로그인 과정에서의 작업 재반복을 제거하여 온보딩 과정의 사용자 경험을 극대화하고 이탈률을 유의미하게 낮췄습니다.

## 7. 문서 분석의 신뢰성 확보: 전용 변환 서버(Aspose) 도입

### 7.1. 문제 상황: 오픈소스 라이브러리의 레이아웃 파괴
초기 오픈소스 기반 텍스트 추출 방식은 수식, 복잡한 표, 도표 내 텍스트를 인식하지 못하거나 계층 구조를 완전히 무시하여 AI 분석 품질을 저해했습니다.

### 7.2. 해결 시도: 고해상도 표준화 인프라 구축
레이아웃 보존율이 가장 높은 상용 엔진(Aspose) 기반의 독립적인 변환 서버를 구축하여 모든 문서를 **표준 고해상도 PDF 및 이미지**로 선행 변환하는 프로세스를 도입했습니다.

**[개선 결과]** 인식률 99% 달성을 통해 AI가 도표의 위치와 텍스트의 관계를 명확히 이해하게 되었으며, 요약 리포트의 신뢰도와 할루시네이션 억제 능력이 획기적으로 개선되었습니다.
